시리즈를 끝내고 방향을 바꿨다. 실무에서 들었던 단어를 하나씩 잡기로 했고, 첫 번째는 변환 도구와 fallback이다. 어제 글 끝에서 "확인하려면 변환 도구 보고서를 봐야 한다"고 써 놓고 그 보고서를 본 적이 없었다.

## 변환 도구는 어디에 서 있나

학습이 끝난 모델은 GPU에서 소수로 돌리라고 만든 파일이다. NPU는 그대로 못 읽는다. 사이를 이어주는 게 변환 도구다.

```
학습 프레임워크 파일   →   교환 형식(ONNX 등)   →   제조사 변환 도구   →   칩에 올리는 파일
                                                        │
                                                        └→ 보고서
```

교환 형식이 가운데 끼는 이유는 단순했다. 프레임워크도 여럿이고 NPU 제조사도 여럿이라 서로 다 맞추면 조합이 폭발한다. 중간에 공용 언어를 하나 두는 것이다. 모델을 "어떤 연산자가 어떤 순서로 연결됐나"라는 그래프로 적은 파일이다.

제조사 도구는 이 그래프를 연산자 하나씩 읽으면서 세 가지를 판정한다. 이 연산자를 내 NPU가 아는가, 양자화 눈금을 어떻게 잡았나, 격자에 올리면 몇 박자 걸리나. 보고서는 결국 층 목록 한 줄씩에 이 판정 셋이 붙은 표다. 어렵게 생긴 파일이지만 구조는 그게 전부다.

## 폴더 구조만 봐도 보이는 것

실제 NPU의 SDK를 하나 열어 봤다. 변환기 본체는 Linux용이라 Mac에서 바로 돌리지는 못했고 폴더 구조만 훑었다. 그런데 그것만으로 위 그림이 그대로 서 있었다. 교환 형식으로 바꾸는 입구, 칩 종류별 변환 엔진, 칩 없이 PC에서 돌려 보는 시뮬레이터, 그리고 카메라 안에서 돌아가는 런타임.

런타임 아래에 CPU용 연산자 소스 파일이 따로 모여 있었다. 파일 이름이 softmax, concat, resize, eltwise, priorbox, proposal이었다. 어제 "검출 후처리와 resize가 fallback으로 잘 간다"고 배웠는데, 제조사가 바로 그 연산자들을 CPU에서 돌릴 코드로 미리 만들어 둔 것이다. 이 폴더가 곧 "이 칩의 NPU가 못 하는 연산자 목록"이었다.

중요한 건 왜 이 몇 개가 CPU로 갔는가라는 공통점이고, 그걸 보려면 각각이 무슨 일을 하는지 한 줄씩만 알면 된다. 두 묶음으로 나뉜다.

```
NPU 격자가 잘하는 일:  곱하고 더하기를 같은 모양으로 수십만 번 반복

CPU로 간 것들
  묶음 A: 곱셈·덧셈이 아닌 계산          → softmax
  묶음 B: 계산은 거의 없고 자리만 바꾸기   → concat, resize, eltwise, priorbox, proposal
```

## softmax: 계산 종류가 다르다

검출 모델 끝에서 "사람일 점수 7.2, 차일 점수 3.1" 같은 점수가 나온다. softmax는 이걸 합이 1이 되는 비율로 바꾸는 단계다. 사람 0.95, 차 0.04 식으로. 그래서 "확신도 95%"라는 말이 나온다.

NPU가 못 하는 이유는 이 과정에 지수 함수와 나눗셈이 들어가기 때문이다. 격자의 MAC은 곱셈기와 덧셈기만 있다. 모델 전체에서 맨 끝 한 번 쓰는 걸 위해 격자 옆에 다른 회로를 깔아 두는 건 낭비라서, 그 한 번은 CPU가 하라고 넘긴다.

그런데 양자화 글에서 추론은 결국 순위만 맞으면 된다고 했다. softmax는 점수를 비율로 바꾸기만 하고 순위는 안 바꾼다. 그러면 softmax를 빼고 점수만으로 순위를 매기면 된다. 실무에서 "모델 마지막 층은 떼고 올린다", "후처리는 밖에서 한다"는 말이 바로 이 작업이었다. 보고서에 softmax 한 줄이 떠 있으면 걱정할 게 아니라 떼면 되는 줄이다.

"확신도 몇 % 이상만 알림" 같은 임계값 기능이 있으면 비율이 필요하긴 하다. 그때도 상자 수백 개 중 상위 몇 개만 골라서 그것만 비율로 바꾸면 된다. 아예 생점수 기준으로 문턱을 정해 두는 곳도 많다고 한다.

## concat: 숫자는 안 바뀌고 자리만 바뀐다

concat은 이어 붙이기다. 격자에서 나온 결과 두 덩어리를 한 덩어리로 나란히 붙이는 것뿐이다. 숫자 하나도 안 바뀐다.

여기서 "자리"라는 말에 걸렸다. 자릿수가 아니고 메모리의 주소, 숫자가 놓여 있는 칸의 위치다.

```
주소:    100  101  102  103  104  105  106  107
A층 결과 │ 7  │ 3  │ 9  │    │    │    │    │    │
B층 결과 │    │    │    │    │    │ 2  │ 8  │ 5  │

concat  │ 7  │ 3  │ 9  │ 2  │ 8  │ 5  │    │    │
```

2, 8, 5는 그대로다. 어느 칸에 들어 있느냐만 변했다. 다음 층이 여섯 개를 연속된 칸에서 한 번에 읽고 싶어 하기 때문이다.

길은 셋이다.

```
① 공짜    B층이 결과를 처음부터 103번 칸에 쓰게 한다. 옮길 일이 사라진다. 컴파일러가 잘하면 이것.
② DMA     메모리에서 메모리로 복사만 하는 작은 회로에 맡긴다. 격자도 CPU도 안 건드린다.
③ CPU     ①②가 안 될 때. 그래서 폴더에 concat 소스가 있다.
```

③으로 떨어지는 흔한 이유 하나가 재미있었다. 양자화 눈금이 서로 다를 때다. 왼쪽 덩어리는 눈금 0.01로 적힌 정수, 오른쪽은 0.03으로 적힌 정수라면 그대로 붙이면 한 덩어리 안에 자가 두 개 섞인다. 한쪽을 다시 반올림해야 하고, 그게 격자의 일이 아니라 CPU로 간다.

그러니 보고서에서 concat이 fallback으로 떠 있으면 두 입력 층의 눈금이 같은지를 봐야 한다. 같으면 자리 이동 문제라 ①로 갈 여지가 있고, 다르면 어딘가가 계산을 해야 한다. 양자화 도구에 "concat으로 들어가는 가지들은 눈금을 하나로 통일하라"는 옵션이 대개 있어서, 정확도를 조금 내주고 fallback 한 줄을 지우는 거래를 사람이 의도적으로 할 수 있다.

## 오늘 정리

```
softmax   계산 종류가 다름(지수, 나눗셈)  → 떼거나, 상위 몇 개만 CPU
concat    계산 0, 자리 이동만             → 눈금 같으면 공짜, 다르면 CPU
```

묶음 B의 공통 원리는 하나다. 숫자를 바꾸지 않고 자리만 바꾸는 일은 격자가 할 일이 아니다. 그걸 누가 하느냐가 칩마다 다르고, 그 차이가 fallback 보고서에 찍힌다. 같은 모델이라도 어떤 칩에서는 concat이 0줄, 어떤 칩에서는 10줄이 뜨는 이유다. 1편부터 계속 나온 "계산은 공짜, 이동이 전부"가 여기서도 그대로였다.

나머지 넷은 concat의 변주라고 한다. resize, eltwise, priorbox, proposal. 다음에 하나씩 같은 질문을 던져 볼 생각이다. 격자가 할 종류의 계산인가, 아니면 자리 이동과 고르기인가.
