얼마 전 어느 회의에서 NPU에 VLM을 올렸을 때 속도 얘기가 나왔다. "입력 처리는 초당 몇천 token, 답 생성은 초당 십몇 token" 하는 식이었다. 같은 모델, 같은 칩인데 두 숫자가 자릿수가 다르게 차이 났다. 이 숫자 놀음을 이해하고 싶다는 생각으로 이번 공부를 진행햇다. 

## token은 글자가 아니다

먼저 걸린 건 단위였다. 초당 12 token이면 초당 글자 12개라고 생각했는데 아니다. token(토큰)은 모델이 글을 자르는 조각이고, 한국어는 글자 하나가 token 하나로 안 떨어진다. 받침 있는 글자가 2~3 token으로 쪼개지기도 한다. 그러니 초당 글자 수는 token 수보다 적다고 보는 게 안전하다.

## 모델이 답 하나 내는 두 단계

모델이 질문 하나에 답하는 과정은 딱 두 단계다.

```
입력: [사진 token 1000개] + [질문 "헬멧 썼어?" token 10개]
          │
          ▼
  ① prefill   입력 1010개를 한꺼번에 처리한다        ← 빠르다
          │
          ▼
  ② decode    답을 1 token씩 쓴다: "네" "," "썼" "습니다"  ← 느리다
```

prefill(프리필)은 입력 token 전부를 모델에 한꺼번에 통과시키는 것이다. 사진과 질문은 이미 다 주어져 있으니 기다릴 게 없다. 1010개를 한 번에 넣는다.

decode(디코드)는 답을 쓰는 것인데, "네" 다음에 뭐가 올지는 "네"를 뽑아 봐야 안다. 그래서 1개씩밖에 못 한다.

하는 일은 사실 같다. token을 모델에 통과시켜서 다음 token 하나를 뽑는 것. 다른 건 **한 번에 통과시키는 token 수**뿐이다. prefill은 1010개, decode는 1개.

## 왜 그 차이가 자릿수 차이가 되나

여기서 지난달 글이 다시 나왔다. 칩이 일하는 시간은 둘이다. 메모리에서 weight(가중치)를 칩 안으로 가져오는 시간, 가져온 weight로 계산하는 시간. 둘 중 긴 쪽이 전체 시간이다.

decode는 token 1개마다 모델 weight **전체**를 메모리에서 가져와야 한다. 그걸로 하는 계산은 token 1개분뿐이다. 창고에서 재료를 다 꺼내 와서 1인분 만들고, 다시 창고 가서 다 꺼내 와서 또 1인분. 시간은 전부 창고 왕복에 들고 요리사는 논다. memory bound(메모리 병목)다.

prefill은 weight를 한 번 가져와서 1010개분 계산을 한다. 재료 한 번 꺼내서 1010인분. 요리사가 바쁘고 창고 왕복은 적다. compute bound(계산 병목)다.

```
decode  : [weight 가져오기] → 1개 계산 → [weight 가져오기] → 1개 계산 → ...
prefill : [weight 가져오기] → 1010개 계산
```

그래서 "decode가 느린 건 메모리가 느려서"라는 말이 된다. 회의에서 하드웨어 쪽이 답 생성 속도를 말하면서 메모리 탓을 한 게 이거였다.

## 메모리 대역폭을 거꾸로 셈해 보기

decode가 token마다 weight 전체를 읽는다면, "모델 크기 × 초당 token 수 ≈ 메모리 대역폭"이다. 이 계산은 맞았다. 다만 모델 크기는 weight 하나를 몇 bit로 저장했냐에 따라 다르다. parameter 100억 개짜리 모델이면 16bit에 20GB, 8bit에 10GB, 4bit에 5GB. 같은 초당 token 수라도 어느 bit였냐에 따라 대역폭 추정이 네 배 차이 난다. 그러니 "8bit라면 얼마"처럼 조건을 붙여서 기억해야 한다.

16, 8, 4는 용량이 아니라 precision(정밀도), weight 하나를 표현하는 bit 수다. 16bit는 압축이 아니라 원본 기준이고, 8과 4가 quantization(양자화)이다. 양자화 글에서 본 그거다.

## 내가 거꾸로 답한 것

클로드가 물었다. "메모리를 두 배 빠른 걸로 바꾸면 prefill도 두 배 빨라지겠네, 맞나? decode는?"

정답은

- decode는 memory bound라서 메모리가 빨라지면 거의 그대로 빨라진다.
- prefill은 compute bound라서 메모리를 아무리 빠르게 해도 요리사가 그대로니 거의 안 빨라진다.

한 줄로 외우기로 했다.

> prefill은 TOPS가 정하고, decode는 memory bandwidth가 정한다.

칩 사양표의 두 숫자가 각각 어느 단계를 알려주는지가 이 한 줄이다.

## 사용자가 느끼는 것

- prefill 시간 = 질문 보내고 **첫 글자가 나올 때까지** 기다리는 시간
- decode 시간 = 그 뒤로 글자가 **타닥타닥 찍히는** 속도

챗봇에서 첫 글자 뜨기 전에 잠깐 멈추는 게 prefill이다.

VLM에서는 사진 한 장이 token 수백~수천 개가 된다. 질문은 10개인데 사진이 1000개면 prefill 할 일의 99%가 사진이다. CCTV처럼 "입력은 사진, 답은 있다/없다"인 일은 decode보다 **prefill이 체감 속도를 정한다.** 입력 사진을 줄이면 prefill이 빨라지는데, 그 대가로 작은 물체가 점 몇 개로 뭉개져서 못 알아보는 문제가 생긴다. 회의에서 나온 고민이 정확히 이거였다.

## KV cache, 그리고 "읽다"의 두 가지 뜻

decode가 "네" 다음을 뽑을 때 앞의 입력 1010개를 돌아봐야 한다. 그럼 매번 prefill을 다시 하는 건가? 아니다. prefill 때 token마다 계산한 중간 결과(K, V라는 두 벡터)를 메모리에 저장해 두고 꺼내 쓴다. 이게 KV cache(키-값 캐시)다. 요청 하나가 끝나면 버린다.

여기서 한 번 꼬였다. "읽다"가 두 뜻으로 쓰이고 있었다.

- 입력을 읽어들인다 = prefill = **계산**. KV를 만들어 내는 것. 요청당 한 번.
- 메모리에서 읽는다 = weight와 KV를 칩 안으로 **가져오는 것**. 계산이 아니라 운반. decode 매 step마다.

KV cache는 첫 번째를 반복 안 하게 해 준다. 두 번째는 그대로다. 오히려 weight 옆에 KV cache까지 가져올 게 하나 더 는다. 그래서 context(문맥)가 길수록 decode는 더 느려진다. 하드웨어 쪽이 속도를 말하면서 "몇 K 기준"이라고 조건을 단 이유다.

```
decode 1 step
  계산: 새 token 1개분만               ← 적다 (KV cache 덕분)
  가져오기: weight 전체 + KV cache 전체  ← 많다 (매번)
```

K, V가 실제로 무슨 계산에 쓰이는지는 attention(어텐션)인데, 거기는 다음에 간다.

## speculative decoding: 노는 요리사한테 일 시키기

decode에서 요리사가 논다면, 재료 꺼낸 김에 더 시키면 된다. speculative decoding(스페큘레이티브 디코딩)은 작은 draft model(초안 모델)이 token 여러 개를 이어서 먼저 쓰고, 큰 target model(타겟 모델)이 그걸 **한 번에** 검증하는 방식이다. weight를 한 번 가져와서 token 1개를 확인하든 5개를 확인하든 시간이 비슷하니까.

```
일반 decode (5 token)
  가져오기→1 | 가져오기→1 | 가져오기→1 | 가져오기→1 | 가져오기→1
  = weight 5번

speculative (draft가 5개 제안, 전부 맞음)
  draft 5개(작아서 빠름) | 가져오기→5개 한 번에 검증
  = weight 1번
```

객관식이 아니라 이어 쓴 문장을 한 번에 교정 보는 쪽이다. 중간에 하나 틀리면 그 뒤는 버리고 틀린 자리는 target 답으로 넣는다. 그래서 최종 출력은 target 혼자 쓴 것과 같다. 품질은 그대로고 속도만 얻는다.

draft가 "별로"여도 품질은 안 떨어진다. 틀리면 target이 걸러내니까. 손해는 속도뿐이다. 자꾸 거부당하면 검증만 헛돌아서 오히려 느려질 수 있다. 그래서 draft의 조건은 똑똑한 게 아니라 "target보다 훨씬 빠를 것"과 "target이 쓸 답을 자주 맞힐 것"이다. 아무 작은 모델이나 붙이면 말투가 달라 자꾸 거부당하니까, target에 맞춰 따로 학습시켜야 한다. 회의에서 "이건 추가 학습이 필요해서 지원이 있어야 한다"고 한 이유다.
